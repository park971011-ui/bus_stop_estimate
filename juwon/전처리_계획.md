# 데이터 전처리 계획

연습 데이터(`data/practice/`)를 직접 확인한 결과를 바탕으로 정리함. 결론: **고칠 건 거의 없고, 피처를 만드는 게 대부분.**

## 1. 데이터 상태 확인 결과

| 항목 | 결과 |
|---|---|
| 결측값 | 없음 |
| 중복 행 | 없음 |
| 거리 `dist_m` | 111~2186m, 이상한 값 없음 |
| 이상하게 빠른 구간 (80km/h 이상) | 없음 |
| 이상하게 느린 기록 (2km/h 미만) | 1,064행 (약 1%) |
| 구간 중앙값보다 5배 이상 오래 걸린 기록 | 192행 (예: 평소 111초 구간이 874초) |
| 노선 끝 구간 | 중앙값 400~800초로 유난히 김 (회차·대기 시간으로 추정) |
| 운행 1회 기록 | 평균 27행. 노선 정류장 수(40~88개)보다 적어서 일부 구간이 빠져 있음 |

## 2. 전처리할 것

### 2-1. 형 변환과 기본 피처
- `route_id`, `from_stop`, `to_stop`을 범주형으로 바꿈.
- 구간 ID를 새로 만듦. `from_stop + "_" + to_stop` 형태.
- `date`에서 `is_weekend`를 만듦. 요일 자체는 쓰면 안 됨.
- 날짜에 맞는 배차간격 하나를 골라 `interval`로 만듦 (평일 `interval_wd`, 토 `interval_sat`, 일 `interval_sun`).
- `first_time`, `last_time`(HHMM 형식)을 분 단위로 바꿈. 예: `545` → 345분.
- 노선의 마지막 구간인지 표시하는 피처를 만듦 (위에서 본 회차 구간 때문).

### 2-2. 구간 통계 피처 (target encoding)
- 구간별 중앙값·평균, 구간×시간대 중앙값, 구간×주말여부 중앙값을 만듦.
- **반드시 fold마다 학습 날짜로만 계산함.** 검증 날짜까지 넣으면 점수가 실제보다 좋게 나옴.

### 2-3. 운행 단위 피처
`date`, `vehicle_id`, `route_id`, `direction`으로 묶으면 운행 1회가 됨.
- 그 차량의 그날 몇 번째 운행인지
- 운행 안에서 몇 번째 구간인지
- 같은 시간대에 운행하는 버스가 몇 대인지 (혼잡도의 대리 지표)

이런 피처는 정답 없이 test에서도 계산할 수 있어서 써도 됨.

### 2-4. 이상치는 바로 지우지 말고 실험으로 판단
- **test에도 이상치가 비슷하게 있음.** 600초 넘는 기록이 train 0.85%, test 0.86%. 학습에서 지운다고 평가가 좋아진다는 보장이 없음.
- **MAE(L1) 손실은 이미 이상치에 강함.** 중앙값을 따라가기 때문.
- **실험할 만한 것:** 학습 데이터에서 "구간 중앙값의 5배 이상" 같은 극단값만 잘라 보고 검증 점수로 판단함. 결과가 좋든 나쁘든 발표의 실험 기록으로 씀.

## 3. 안 해도 되는 것 / 하면 안 되는 것

| 항목 | 이유 |
|---|---|
| 정규화와 표준화 | 안 해도 됨. 트리 모델은 값의 크기에 영향을 받지 않음 |
| 정답에 로그 변환 | 안 해도 됨. L1 손실을 쓰면 효과가 거의 없음 |
| `row_id` 사용 | 단순한 번호라서 의미가 없음 |
| 요일 원본 사용 | train과 test의 요일이 하나도 겹치지 않음 |
| 정류장 이름으로 구분 | 같은 이름이 여러 ID에 붙어 있어서 ID로 구분해야 함 |
| 앞 구간의 `tt_sec` 사용 | test에는 정답이 없어서 계산할 수 없음 |
| test 정답 추정 | 대회 규칙 위반 |
