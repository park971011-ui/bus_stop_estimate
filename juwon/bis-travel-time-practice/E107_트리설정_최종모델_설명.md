- 제출 파일: `submissions/final_E107_mc5_hoursum.csv`
- 만드는 법 (순서대로):
  1. `scripts/E103_cache_folds.py`: 검증용·최종용 학습 데이터 준비 (피처는 E89 MD 48개 그대로)
  2. `scripts/E103_tune.py L_511mc5:final W_255mc5:final C_base:final`: 목·금 모델 학습
  3. `scripts/E104_sunday_make.py`: 일요일 모델 학습

- public 기록: E89 MD **24.098** → E105 **23.950** (트리 크기 키움) → E107 **23.895** (3등)

## 1. 트리(결정 트리)란

트리는 **질문을 이어 붙여 답을 고르는 순서도**라고 보면 됨. 우리 데이터라면 이런 식:

```
회차 구간인가?
├─ 예 → 출근 시간대인가?
│        ├─ 예 → 예측 420초
│        └─ 아니오 → 예측 300초
└─ 아니오 → 거리가 500m 넘나?
         ├─ 예 → 예측 130초
         └─ 아니오 → 예측 70초
```

- 맨 끝 칸(예측값이 있는 곳)이 **잎(leaf)**. 위 그림은 잎이 4개고, 최종 모델은 트리 하나에 잎이 최대 **511개**.
- 각 잎의 예측값은 그 칸에 들어간 학습 데이터 통행시간의 **중앙값**. MAE(L1)로 학습해서 평균이 아니라 중앙값을 씀 (이유는 `E67_최종모델_설명.md` 7절).
- 질문과 기준값(500m, 출근 시간대 등)은 사람이 정하지 않음. 모델이 오차를 가장 많이 줄이는 질문을 데이터에서 직접 찾음.
- **LightGBM**은 이런 트리를 **1500개** 쌓음. 첫 트리가 대충 맞히면 다음 트리는 앞 트리가 틀린 부분만 고치는 식(그래디언트 부스팅)이고, 최종 예측은 1500개를 합친 값.
- 대회 규칙(EVALUATION.md 5절)의 허용 모델은 XGBoost, LightGBM, CatBoost, RandomForest, ExtraTrees 등 **트리 앙상블 계열**. 우리가 쓴 LightGBM·CatBoost·ExtraTrees 모두 허용 목록에 있음.

## 2. 트리를 어떻게 구성했나 (최종 설정)

| 설정 | 뜻 | 예전 (E89까지) | **최종 (E107)** |
|---|---|---|---|
| `num_leaves` (잎 수) | 트리 하나가 데이터를 몇 칸까지 나눌 수 있나 | 127 | **511** (4일 모델) / **255** (평일 전용) |
| `min_child_samples` (잎당 최소 행) | 한 칸에 최소 몇 행이 있어야 나눌 수 있나 | 10 | **5** |
| `n_estimators` (트리 수) | 트리를 몇 개 쌓나 | 1500 | 1500 (그대로) |
| `learning_rate` (학습률) | 트리 하나가 앞 오차를 얼마나 고치나 | 0.02 | 0.02 (그대로) |
| `subsample`, `colsample_bytree` | 트리마다 행·피처를 몇 %만 보고 만드나 | 0.8, 0.8 | 그대로 |
| 손실 함수 | 무엇을 줄이도록 학습하나 | L1 (MAE) | 그대로 |
| 범주형 | 숫자가 아닌 피처 | `route_id`, `seg_id` | 그대로 |

**한 줄 요약:** 트리를 **더 크게, 더 잘게** 나누도록 바꿈. 예전 설정은 피처가 35개쯤일 때 정한 값인데, 피처가 48개로 늘면서 배울 패턴이 많아졌는데도 트리 크기가 그대로라 다 담지 못하고 있었음.

## 3. 왜 그 값인가 (검증 결과)

검증: 대회 train 평일(월·화·수)을 하루씩 빼고 나머지로 학습 → 빠진 날 MAE (3-fold, 날짜 단위). 숫자는 모델 하나만 쓴 MAE.

### 4일 모델 (월·화·수·토 학습)

| 잎 수 | 잎당 최소 행 | 트리 수 | MAE | |
|---|---|---|---|---|
| 127 | 10 | 1500 | 23.268 | 예전 설정 |
| 255 | 20 | 1500 | 23.139 | |
| 511 | 20 | 1500 | 23.106 | |
| 1023 | 20 | 1500 | 23.218 | 너무 큼 |
| 511 | 20 | 3000 | 23.143 | 트리 많으면 나빠짐 |
| 511 | 2 | 1500 | 23.068 | 너무 잘게 나눔 |
| **511** | **5** | **1500** | **23.041** | **최종** |

### 평일 전용 모델 (월·화·수만 학습)

| 잎 수 | 잎당 최소 행 | 트리 수 | MAE | |
|---|---|---|---|---|
| 127 | 10 | 1500 | 23.229 | 예전 설정 |
| 255 | 20 | 1500 | 23.177 | |
| 255 | 20 | 3000 | 23.199 | |
| 511 | 5 | 1500 | 23.188 | 너무 큼 |
| **255** | **5** | **1500** | **23.121** | **최종** |

### 효과 없던 것

| 바꾼 것 | 4일 모델 | 평일 전용 |
|---|---|---|
| 학습률 0.01 + 트리 3000 | 23.238 (−0.03) | 23.215 (−0.01) |
| 열 샘플링 0.5 | 23.279 (+0.01) | 23.211 (−0.02) |
| 잎당 최소 행 30 + L2 규제 5 | 23.316 (+0.05) | 23.317 (+0.09) |

### 해석

- 트리를 키울수록 좋아지다가 **어느 지점부터 다시 나빠짐** (잎 1023, 최소 행 2, 트리 3000).
- 너무 크면 학습한 날짜의 우연한 패턴까지 외워서, 처음 보는 날짜(목·금)에서 틀림 (과적합).
- 평일 전용 모델은 학습 데이터가 3일로 더 적어서, 4일 모델보다 작은 크기(잎 255)에서 가장 좋음.
- 규제를 세게 거는 방향(최소 행 30, L2 규제)은 모두 나빠짐 → 예전 모델은 **과적합이 아니라 너무 작은 것**이 문제였음.

## 4. 모델 섞기

### 목·금 (80,715행)

```
목·금 = 0.9 × [ 0.5 × (0.9 × 4일 LGB 잎511 + 0.1 × CatBoost)
              + 0.5 × 평일 전용 LGB 잎255 ]
      + 0.1 × ExtraTrees (평일 전용, MAE 기준)
→ 시간 합 후처리 (frac 0.25)
```

| 모델 | 학습 데이터 | 트리 설정 |
|---|---|---|
| 4일 LightGBM | 대회 train 월·화·수·토 | 잎 511, 최소 행 5, 1500개 |
| CatBoost | 대회 train 월·화·수·토 | 깊이 10, 2000개, 학습률 0.08 |
| 평일 전용 LightGBM | 대회 train 월·화·수 | 잎 255, 최소 행 5, 1500개 |
| ExtraTrees (E101) | 대회 train 월·화·수 | 100개, 잎당 최소 10행, 피처 60% |

- ExtraTrees는 LightGBM과 트리 만드는 방식이 달라서(기준값을 무작위로 고름), 섞으면 서로의 실수를 덮어 줌.

### 일요일 (30,848행)

```
일요일 = 0.8 × (LGB 기본 잎127 + LGB 잎511) / 2 + 0.2 × CatBoost
→ 시간 합 후처리 (frac 0.4)
```

- 학습: 대회 train + 연습 train + 연습 test (진짜 일요일 포함), 피처는 E73 그대로 (같은 날 연습 기록 6개 포함)
- 배차가 토·일 다른 노선(2·704·B1)은 일요일 행 가중치 ×2 (E67)
- 일요일은 연습 노선 빼기 검증에서 잎 511 하나만 쓰면 노선 605가 크게 나빠져서(+0.51), 기본과 평균을 냄: 27.340 → 27.238 (4개 노선 중 3개 개선)

## 5. 시간 합 후처리 (E106, `scripts/hour_sum_adjust.py`)

**아이디어:** 버스 한 대가 한 시간(예: 8시) 동안 출발한 구간들의 통행시간을 다 더하면 약 3600초여야 함.

- 조건: 그 차량이 앞 시(7시)와 뒤 시(9시)에도 기록이 있고, 중간에 기록이 끊기지 않은 칸만
- 목표 합 = 3600 + (그 시 마지막 행 − 앞 시 마지막 행) / 2 (시작·끝 행이 정각에 걸친 만큼 보정)
- 예측 합과 목표 합의 차이 중 **일부(평일 25%, 일요일 40%)를 그 시간의 회차 행에** 더함 (회차 행이 없으면 예측값 비율로 나눔)
- 입력 컬럼(`arrive_hour`, 정류장 순서)과 예측값만 씀. 정답은 안 씀

| 검증 | 후처리 전 | 후처리 후 |
|---|---|---|
| 평일 3-fold (frac 0.25) | 23.056 | 23.010 (−0.046, 3/3) |
| 연습 일요일 노선 빼기 (frac 0.4) | 27.238 | 26.977 (−0.26, 4/4) |

- 정답으로 확인: 끊김 없는 칸은 정답 합 − 3600 중앙값이 **+3초**로 정확함. 반대쪽 종점에서 방향이 바뀌는 칸은 **+1,229초**(기록 없는 종점 대기)라 쓸 수 없어서 뺌
- 100%가 아니라 일부만 나누는 이유: 차이를 어느 행이 만들었는지 모르기 때문. 다 나누면 오히려 나빠짐 (E90, E102)
- E94(일요일 회차 ×1.227)와 다른 점: E94는 연습 노선의 배율을 대회 노선에 그대로 옮겼다가 실패. 이번에는 대회 test 자체의 시간 구조로 버스·시간마다 따로 계산함
